# Connected accounts setup

Current state: Zebra supports explicit LinkedIn and GitHub **identity linking** from Settings → Account & Security. Full connected profile evaluation is **FAIL / unavailable** until provider setup and data-access work are completed. A linked identity alone does not supply LinkedIn experience/skills or authorize GitHub repository reads.

## Manual owner steps, in order

1. **Choose a stable callback host for each environment.** Set `BETTER_AUTH_URL` to that origin. OAuth callbacks are `https://YOUR_HOST/api/auth/callback/linkedin` and `https://YOUR_HOST/api/auth/callback/github`. For local development, use `http://localhost:3000/api/auth/callback/...`. Register separate provider apps for local and production if callback restrictions require it.
2. **LinkedIn Developer Portal:** create a Zebra application, complete its company association and verification, add the **Sign In with LinkedIn using OpenID Connect** product, then register the LinkedIn callback URL. Copy its Client ID and Client Secret into server-only `LINKEDIN_CLIENT_ID` and `LINKEDIN_CLIENT_SECRET` for the correct environment. Do not add posting permissions for this read-only feature.
3. **GitHub Developer Settings:** register a **GitHub App** owned by the intended Zebra organization. User authorization callback stays `https://HOST/api/auth/callback/github`. Setup URL is `https://HOST/api/github/install/callback` (not the Better Auth callback). Webhook URL is `https://HOST/api/github/webhook`. Leave “Request user authorization (OAuth) during installation” off. Repository access is “Only select repositories.” Permissions are Metadata: Read and Contents: Read. Subscribe only to `installation` and `installation_repositories`. Copy the App's OAuth Client ID and Client Secret into server-only `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`. Copy the App ID, slug, PEM private key, and webhook secret into server-only `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`, and `GITHUB_WEBHOOK_SECRET`. Never use a `NEXT_PUBLIC_` name for those values. In a single-line env value, encode PEM newlines as `\n`.
4. **Deploy configuration:** set the LinkedIn and GitHub OAuth credentials plus the four GitHub App values in the hosting environment and redeploy. Apply migration `0014_github_installations` before opening the install flow. Never put secrets in `NEXT_PUBLIC_*`, commit them, or paste them into an issue/chat. Existing Better Auth `BETTER_AUTH_SECRET` must remain stable because OAuth state, the install state cookie, and encrypted tokens depend on it. Coordinate migration/re-authorization of any older unencrypted provider tokens when turning on `encryptOAuthTokens`.
5. **Manual consent test:** sign in to a Zebra test account using its existing login, open `/dashboard/settings?tab=account`, connect each provider, approve consent, and verify return to the same Zebra user. Check that disconnect removes the linked account and reconnect works. Also test denial and a provider account with a different email.

## What the product does after those values are set

Settings → Account & Security links GitHub with `read:user` and `user:email` only. Install repositories then opens the GitHub App installation flow. Sync mints a one-hour installation token on the server, does not store it, and lists only repositories GitHub returns for that installation. A repository becomes an evidence node only after the user accepts it, and only when authorship is the linked owner or a matching commit author and GitHub reports a language. Removing the installation deletes local snapshots and asks GitHub to delete the installation. Accepted evidence stays.

## Remaining engineering gates

- Keep LinkedIn user-supplied export for full profile evaluation. LinkedIn's OIDC userinfo is limited; richer Profile API access requires LinkedIn approval. Add extra permissions only after approval and an updated consent screen.
- Add provider revocation on LinkedIn disconnect and GitHub user-token revocation. Installation removal already deletes the GitHub App installation.
- Add token-rotation handling, capability-level status, and live provider tests. Until then, show full connected evaluation as **FAIL / unavailable**, not as a completed capability.
